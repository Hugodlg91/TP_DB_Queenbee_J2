## Notre propre code

Constats trouvés en relisant notre code, au-delà des failles imposées :

- **R1 (haute) : l'administrateur pouvait lire les hachés des mots de passe, par le journal et par la table.**
  - *Preuve* : en `admin`, `UPDATE utilisateur SET mot_de_passe_hash = '$argon2id$...' WHERE login = 'm.ba';`, puis `SELECT apres ->> 'mot_de_passe_hash' FROM journal_audit ORDER BY id DESC LIMIT 1;` renvoie le haché en clair. Corriger le journal ne suffisait pas : l'admin avait `SELECT` sur toute la table `utilisateur`. En `admin`, `SELECT mot_de_passe_hash FROM utilisateur;` renvoyait 11 lignes (vides dans notre jeu d'essai, mais la colonne était lisible).
  - *Correction* : dans `audit_ligne()` (`corrections.sql`), `to_jsonb(...) - 'mot_de_passe_hash'`. Dans `roles.sql`, des droits par colonne pour `qb_admin`, sans `mot_de_passe_hash` : `SELECT (id, login, role, site_id, apicultrice_id)`, `INSERT` et `UPDATE (login, role, site_id, apicultrice_id)`, après un `REVOKE ALL ON utilisateur FROM qb_admin` qui retire l'ancien droit à la relance.
  - *Retest* : `apres ? 'mot_de_passe_hash'` vaut `f`. En `admin`, `SELECT mot_de_passe_hash FROM utilisateur;` donne `ERROR: permission denied for table utilisateur` ; `SELECT login, role FROM utilisateur`, la création d'un compte et `UPDATE utilisateur SET site_id = site_id WHERE login = 'm.ba'` passent toujours. La preuve d'origine (`UPDATE ... SET mot_de_passe_hash` en `admin`) est désormais refusée elle aussi : elle se rejoue en `postgres`.
- **R2 (haute : règle métier contournée) : le trigger du lab 6 cédait à deux inscriptions simultanées.**
  - *Preuve* : deux sessions inscrivent Mariama Ba chez Moussa Sarr et chez Ibrahima Fall (deux formateurs varroa) : `INSERT 0 1` et `INSERT 0 1`. Résultat : `varroa | {Ibrahima Fall, Moussa Sarr}`.
  - *Correction* : le trigger verrouille la ligne de l'apicultrice avant de vérifier. En le relisant, nous avons aussi corrigé sa condition, reprise du modèle GreenFarm du sujet : un `UPDATE` qui remplace le formateur par un autre du même thème était refusé à tort, car l'ancienne ligne, encore visible, passait pour « un autre formateur ». La ligne modifiée est maintenant exclue.
  - *Retest* : B attend (2 s, la durée de la transaction de A), puis reçoit `DF violée : cette apicultrice a déjà un formateur pour ce thème`. Le remplacement de Moussa Sarr par Ibrahima Fall pour Awa Diop donne `UPDATE 1` ; un second formateur varroa, seul ou dans un `INSERT` de deux lignes, est toujours refusé. Limite : le verrou ne protège qu'en `READ COMMITTED` (le niveau par défaut). En `REPEATABLE READ`, B attend aussi, puis passe : `{Ibrahima Fall, Moussa Sarr}`. Une contrainte `UNIQUE` garantit la règle à tout niveau d'isolation (`SERIALIZABLE` la protège aussi, mais par une erreur de sérialisation qu'il faut réessayer).
- **R5 (moyenne : défense en profondeur absente) : une récolte pouvait être déclarée en quantité ou à une date impossible.**
  - *Preuve* : en `a.diop`, sur une base sans la correction, `INSERT INTO v_mes_recoltes (ruche_id, date_recolte, quantite_kg) VALUES (:'ma_ruche', DATE '2027-03-15', 'NaN');` donne `INSERT 0 1`, de même que 9999.99 kg en l'an 3027 ; `v_mes_recoltes` montre alors `NaN` et `9999.99` au statut `declaree`. `recolte_quantite_positive` (`quantite_kg > 0`, jour 1) laisse passer NaN, car pour PostgreSQL NaN est plus grand que tout nombre. Le coordinateur qui valide reste un garde-fou : d'où la gravité moyenne.
  - *Correction* : dans `check.sql`, deux contraintes nommées, sans toucher à celle du jour 1 : `recolte_quantite_plausible` (`quantite_kg > 0 AND quantite_kg <= 200` ; `NaN <= 200` est faux, NaN est donc refusé) et `recolte_date_plausible` (`date_recolte BETWEEN DATE '2020-01-01' AND DATE '2100-01-01'`). La valeur 'infinity' en kg était déjà refusée par le type `numeric(6,2)`. Toutes les récoltes existantes respectent ces règles.
  - *Retest* : `1_schema_normalise/tests_8_1_8_2.sql`, tests 5 à 10. NaN et 9999.99 donnent `violates check constraint "recolte_quantite_plausible"` (y compris par la vue, en `a.diop`) ; l'an 3027 et 'infinity' en date donnent `violates check constraint "recolte_date_plausible"` ; 'infinity' en kg donne `numeric field overflow` ; aucune ligne existante hors règles.
- **R6 (moyenne : défense en profondeur absente) : une personne pouvait agir sous le nom de son groupe.**
  - *Preuve* : en `postgres`, `SET SESSION AUTHORIZATION "admin"; SET ROLE qb_admin; UPDATE utilisateur SET site_id = site_id WHERE login = 'm.ba';` donne `UPDATE 1`, et la dernière ligne du journal est `qb_admin | utilisateur | UPDATE`. `qui()`, reprise du sujet, lit le paramètre `role` : le journal nomme alors le groupe, et plus la personne. Pour les apicultrices, c'est sans effet (les vues filtrées par `qui()` sont vides pour `qb_apicultrice`), mais l'admin a des droits directs sur des tables. Ce constat complète C6, qui ne testait que `SET ROLE "admin"`.
  - *Correction* : dans `roles.sql`, les appartenances sont données `WITH INHERIT TRUE, SET FALSE` (PostgreSQL 16 et plus) : la personne hérite des droits du groupe, mais ne peut plus devenir le groupe.
  - *Retest* : la même commande donne `ERROR: permission denied to set role "qb_admin"` ; connecté en `a.diop`, `SET ROLE qb_apicultrice` est refusé de la même façon. Les droits hérités marchent toujours (l'admin lit le journal, `a.diop` lit `v_mes_ruches`), `SET ROLE "a.diop"` depuis `postgres` aussi, et les 12 tests de contournement redonnent les mêmes résultats.

## Testez-vous · Lab 10

1. **Pourquoi `conn.execute("... ORDER BY %s", (tri,))` ne trie-t-il pas par la colonne choisie ?** `%s` envoie une **valeur**, pas un nom de colonne. La base trie donc par la constante `'code'`, la même pour toutes les lignes : l'ordre ne change pas. Un nom de colonne ne peut pas être un paramètre ; il faut une liste blanche et `sql.Identifier`.
2. **L'injection empilée a échoué : `recherche_vuln.py` est-il sûr pour autant ?** Non. Les attaques **par erreur** et **à l'aveugle** passent, et elles lisent le téléphone d'Awa Diop (P1). L'échec de l'empilement vient seulement du protocole des requêtes à paramètres, qui n'accepte qu'une commande. Il ne protège pas d'une sous-requête glissée dans le `ORDER BY`.
3. **Quelle différence entre `security_barrier` et `security_invoker` ?** Ce sont deux choses différentes, qui se combinent.
   - `security_barrier` change **l'ordre d'évaluation** : les conditions de la vue sont appliquées avant toute fonction non sûre fournie par l'utilisateur. Une fonction espion ne voit donc que les lignes autorisées.
   - `security_invoker` change **les droits** : la vue s'exécute avec les droits de **celui qui la lit**, et non de son propriétaire. Une vue `security_invoker` n'aurait pas pu lire `apicultrice` pour une apicultrice, ce qui aurait empêché P2, mais aussi nos vues filtrées, qui reposent justement sur les droits du propriétaire.
4. **Classement par gravité.**
   - La vue `v_carte_ruches` d'origine est **critique** : elle fuit les données personnelles et les positions de toutes les apicultrices.
   - Une fonction `SECURITY DEFINER` sans `search_path` est **haute** : un utilisateur peut glisser un objet à lui, par exemple une fausse `qui()` ou une fausse table `journal_audit`, qui s'exécutera avec les droits du propriétaire. C'est une règle de sécurité contournée et une élévation de privilège possible.
   - Un README absent est **bas** : c'est une bonne pratique.
